# Circle Wallet

Небольшой fullstack-криптокошелёк на **Circle Developer-Controlled Wallets** в тестовой сети **BASE-SEPOLIA**.
Пользователь пополняет кошелёк тестовыми токенами, выводит их на любой адрес и видит баланс и историю операций.
Circle выполняет переводы и сообщает о них вебхуками, приложение само ведёт балансы и историю.

- **Бэкенд** — Express + TypeScript (`apps/backend`): работа с Circle API, приём вебхуков, учёт балансов.
- **База** — Supabase / Postgres (`supabase/migrations`): пользователи, балансы, история операций.
- **Фронтенд** — Next.js + Mantine (`apps/web`): интерфейс, RU/EN.

## Требования

| Что | Версия | Зачем |
|---|---|---|
| Node.js | ≥ 20 (проверено на 24) | бэкенд, фронтенд, скрипты |
| pnpm | ≥ 10 (проверено на 11) | монорепо на pnpm workspaces: `npm i -g pnpm` или `corepack enable` |
| Docker | Docker Desktop или аналог, запущен | локальный Supabase (`pnpm db:start`) |
| Аккаунт Circle | бесплатный, testnet | только для варианта Б — с настоящими кошельками |

## Быстрый старт

Общие шаги для обоих вариантов:

```bash
pnpm install
pnpm db:start                                     # Supabase в Docker + все миграции из supabase/migrations
cp apps/backend/.env.example apps/backend/.env
cp apps/web/.env.example apps/web/.env.local      # менять ничего не нужно
```

Шаблон `apps/backend/.env` уже настроен на локальный Supabase (стандартный демо-ключ Supabase CLI, одинаковый для
всех локальных установок), править в нём для базы ничего не нужно. Осталось указать Circle — вариант А или Б.

### Вариант А: без аккаунта Circle (mock)

Самый быстрый способ увидеть все сценарии. Локальный mock реализует используемые эндпоинты Circle, подписывает
вебхуки так же, как Circle, и сам переводит статусы переводов: `INITIATED → QUEUED → SENT → COMPLETE`.

1. Запустите mock (отдельный терминал), он работает на `:4010`:
   ```bash
   pnpm --filter @circle-wallet/backend circle:fake
   ```
2. В `apps/backend/.env` укажите (эти строки есть в шаблоне закомментированными, секрет mock печатает при старте):
   ```
   CIRCLE_BASE_URL=http://localhost:4010
   CIRCLE_API_KEY=TEST_API_KEY:fake:fake
   CIRCLE_ENTITY_SECRET=abababababababababababababababababababababababababababababababab
   ```
3. Запустите приложение:
   ```bash
   pnpm dev                                       # backend :4000 + web :3000
   ```
4. Откройте http://localhost:3000, создайте пользователя («Новый») и скопируйте его адрес.
5. Пополнение (вместо фаусета):
   ```bash
   curl -X POST localhost:4010/_fake/deposit -H 'content-type: application/json' \
        -d '{"address":"0x<адрес пользователя>","amount":"25"}'
   ```
   В истории появится «В обработке», через ~3 секунды — «Выполнен», 25 USDC станут доступны.
6. Вывод — форма «Вывод» на любой адрес `0x…`. Сумма **`13.13`** в mock заканчивается статусом `FAILED`:
   так видно неуспешный вывод и возврат средств.

> Пользователи, созданные с mock, получают фейковые кошельки. Перед переходом на настоящий Circle пересоздайте
> базу: `pnpm db:reset`.

### Вариант Б: с настоящим Circle (testnet)

1. **API key.** Зарегистрируйтесь на https://console.circle.com (бесплатно), режим Testnet → Keys → Create a key →
   Standard key. В `apps/backend/.env`:
   ```
   CIRCLE_BASE_URL=https://api.circle.com
   CIRCLE_API_KEY=TEST_API_KEY:...
   ```
2. **Entity Secret** — секрет для подписи операций с кошельками. Сгенерировать и зарегистрировать:
   ```bash
   pnpm --filter @circle-wallet/backend circle:entity-secret
   ```
   Скрипт напечатает строку `CIRCLE_ENTITY_SECRET=<64 hex-символа>` — вставьте её в `apps/backend/.env`.
   Recovery file сохраняется в `apps/backend/recovery_file_*.dat` (в .gitignore) — это **не** секрет, а файл
   для его сброса. Сохраните и то и другое: секрет регистрируется один раз.
3. **Запуск:**
   ```bash
   pnpm dev
   ```
   Откройте http://localhost:3000 и создайте пользователя — у него появится настоящий адрес в Base Sepolia.
4. **Вебхуки** (необязательно, но без них обновления приходят только опросом раз в 30 секунд). Circle нужен
   публичный HTTPS-адрес бэкенда:
   ```bash
   ngrok http 4000                                # или: cloudflared tunnel --url http://localhost:4000
   pnpm --filter @circle-wallet/backend circle:subscribe-webhook https://<адрес туннеля>/webhooks/circle
   ```
   Адрес туннеля меняется при перезапуске (кроме постоянного домена ngrok) — тогда подписку нужно создать заново.
5. **Тестовые токены** — кнопка «Пополнить» в карточке пользователя → https://faucet.circle.com → **USDC** и сеть
   **Base Sepolia** → адрес пользователя. Проверьте сеть: фаусет может предложить другую (например, Arc Testnet),
   и тогда токены уйдут туда. Лимит фаусета — один запрос в 2 часа на адрес и токен.

## Как пользоваться

1. **Создать пользователя** — кнопка «Новый» справа вверху → имя → «Создать». Бэкенд создаёт пользователю
   отдельный кошелёк Circle; его адрес — адрес для пополнения. Переключение — выпадающий список рядом.
2. **Пополнить** — кнопка «Пополнить»: адрес, QR-код, ссылка на фаусет. Пополнение появляется в истории со статусом
   «В обработке» и колонкой «Поступает» в балансе, а после `COMPLETE` в Circle (на Base Sepolia — несколько минут)
   становится «Выполнен» и переходит в «Доступно».
3. **Вывести** — форма «Вывод»: адрес получателя (`0x…`), сумма (MAX — весь доступный баланс) → «Вывести». Сумма
   сразу резервируется («Выводится»), статус доходит до «Выполнен» или «Не выполнен» (тогда средства
   возвращаются). Для проверки удобно вывести на адрес второго своего пользователя — у него появится пополнение.
4. **Баланс и история** обновляются сами: вебхуками Circle, без них — опросом раз в 30 секунд или кнопкой
   «Синхронизировать». История постраничная — «Показать ещё» внизу.
5. **Язык** — переключатель RU / EN справа вверху.

## Тестирование

### Автотесты

| Команда | Что нужно | Что запускается |
|---|---|---|
| `pnpm test` | ничего | unit-тесты: разбор сумм, подпись вебхуков (интеграционные пропускаются) |
| `pnpm test:integration` | запущенный локальный Supabase (`pnpm db:start`) | все тесты: unit + интеграционные |

**Интеграционные тесты** гоняют весь HTTP-стек бэкенда против настоящего Postgres; Circle подменён фейком в
памяти (`apps/backend/test/fakeCircle.ts`), поэтому ни аккаунт Circle, ни сеть не нужны. Покрыто:

- создание пользователя с кошельком; проверка подписи вебхуков;
- пополнение: `pending → completed`, повторные и запоздавшие вебхуки, догоняющая синхронизация без вебхука;
- вывод: резерв, завершение, неуспех с возвратом средств, отказ Circle, повтор после сбоя Circle;
- 5 параллельных выводов не уводят баланс в минус;
- `Idempotency-Key`: повтор, 5 параллельных повторов, ключ с другими параметрами;
- точные суммы: входящие записываются как есть, «битая» транзакция не останавливает сверку;
- пагинация истории: 120 операций с одинаковым временем без пропусков и повторов;
- неизменяемость учёта: правка суммы, откат или правка завершённой операции, удаление, прямая запись в баланс
  отклоняются базой; удаление пользователя удаляет его историю;
- после всех сценариев сохранённые балансы совпадают с пересчётом по истории (`balance_drift()`).

`pnpm test:integration` сам берёт адрес и ключ из `supabase status`. Тесты пишут в ту же локальную базу, что и
приложение, и удаляют всё, что создали.

### Ручная проверка сценариев из ТЗ

| Сценарий | Как проверить |
|---|---|
| Пользователь | «Новый» → имя → в списке появился пользователь со своим адресом |
| Пополнение | mock: `curl … /_fake/deposit`; Circle: фаусет → в истории «В обработке» → «Выполнен» |
| Вывод | форма «Вывод» → в истории «В обработке» → «Выполнен»; mock, сумма `13.13` → «Не выполнен» и возврат |
| Баланс и история | «Доступно» / «Поступает» / «Выводится» меняются вместе со статусами; «Показать ещё» в истории |
| Двойной вывод | отправить один и тот же вывод дважды с одним `Idempotency-Key` (команда ниже) — второй ответ `200` с заголовком `Idempotent-Replayed: true`, вывод один |

```bash
curl -i -X POST localhost:4000/api/users/<id>/withdrawals -H 'content-type: application/json' \
  -H 'Idempotency-Key: demo-1' -d '{"tokenId":"<token id>","destinationAddress":"0x…","amount":"1"}'
```

(`<token id>` — `balances[].token.id` из `GET /api/users/<id>`.)

## Настройка подробно

### Supabase

- **Локально (по умолчанию):** `pnpm db:start` / `pnpm db:stop`; `pnpm db:reset` пересоздаёт базу (данные
  удаляются). Новые миграции на существующую базу: `pnpm exec supabase migration up --local`.
- **Облачный проект:** создайте проект на supabase.com, затем
  ```bash
  pnpm exec supabase link --project-ref <ref>
  pnpm db:push
  ```
  `SUPABASE_URL` и `service_role` key — в Project Settings → API.

Бэкенд ходит в базу только с ключом `service_role`. RLS включён на всех таблицах без политик: у anon/authenticated
доступа нет, фронтенд работает только через API бэкенда.

### Circle

- **Wallet set** создаётся автоматически при создании первого пользователя, его id сохраняется в таблице
  `app_settings`. Можно задать готовый через `CIRCLE_WALLET_SET_ID`.
- **Вебхуки** можно подписать и в консоли: Webhooks → Add subscription → `https://<host>/webhooks/circle`.
  Circle проверяет адрес запросом `HEAD`, бэкенд отвечает `200`.
- **Без вебхуков** приложение тоже работает: фоновая сверка опрашивает Circle каждые `RECONCILE_INTERVAL_MS`.

## API бэкенда

Базовый URL `http://localhost:4000`. Аутентификации нет (по ТЗ); вебхуки защищены подписью Circle. JSON, успешные ответы `{ "data": ... }`, ошибки
`{ "error": { "code", "message", "details?" } }`. Все суммы передаются **десятичными строками** (`"10.5"`).
Типы описаны в `packages/shared/src/index.ts`.

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/health` | healthcheck |
| `GET` | `/api/users` | список пользователей |
| `POST` | `/api/users` | создать пользователя `{ "name": "Alice" }`, создаёт ему кошелёк Circle, отвечает `201` и `User` |
| `GET` | `/api/users/:id` | пользователь + балансы (`UserDetails`) |
| `GET` | `/api/users/:id/transactions?limit=&cursor=` | история операций, новые сверху, постранично (`limit` 1–200, по умолчанию 50) → `{ data, nextCursor }` |
| `POST` | `/api/users/:id/withdrawals` | вывод `{ tokenId, destinationAddress, amount }`, заголовок `Idempotency-Key` (рекомендуется) → `201` и `Transaction`; повтор с тем же ключом → `200` |
| `POST` | `/api/users/:id/sync` | принудительная сверка кошелька пользователя с Circle → `{ updated }` |
| `HEAD/POST` | `/webhooks/circle` | приём уведомлений Circle |

**User**: `{ id, name, address, blockchain, circleWalletId, createdAt }`

**Balance** (по каждому токену):
- `available` — доступно к выводу: завершённые пополнения минус все не-failed выводы;
- `incoming` — пополнения, которые Circle уже видит, но которые ещё не `COMPLETE`;
- `outgoing` — выводы в обработке (уже зарезервированы и вычтены из `available`).

**Пагинация истории — курсорная.** Ответ: `{ "data": [...], "nextCursor": "..." | null }`. Следующая (более старая)
страница — тот же запрос с `?cursor=<nextCursor>`; `null` — страниц больше нет. Курсор непрозрачный (позиция
`created_at` + `id` последней операции страницы), неверный курсор или `limit` → `400`.

**Transaction**: `{ id, userId, direction: deposit|withdrawal, status: pending|completed|failed, circleState,
circleTransactionId, token, amount, sourceAddress, destinationAddress, txHash, explorerUrl, errorReason, createdAt,
updatedAt }`

Статусы. Наш `status` — упрощённый жизненный цикл, сырой статус Circle виден в `circleState`:

| Circle state | status |
|---|---|
| `INITIATED`, `CLEARED`, `QUEUED`, `SENT`, `STUCK`, `CONFIRMED` | `pending` |
| `COMPLETE` | `completed` |
| `FAILED`, `DENIED`, `CANCELLED` | `failed` |

Ошибки вывода:
- `400 bad_request` / `validation_error` — неверный адрес, сумма, точность или токен;
- `422 insufficient_funds` — сумма больше доступного баланса;
- `422 idempotency_key_reused` — `Idempotency-Key` уже использован для вывода с другими токеном, суммой или адресом;
- `404 not_found` — пользователь не найден;
- `502 circle_error` — Circle недоступен при создании пользователя.

Если Circle отклонил перевод (4xx), вывод возвращается со статусом `201`, `status: "failed"` и `errorReason`.

**Идемпотентность вывода.** Клиент передаёт `Idempotency-Key: <строка до 255 символов: буквы, цифры, _ . : ->`.
Повтор запроса с тем же ключом (двойной клик, повтор после обрыва связи, две вкладки) не создаёт второй вывод и
не резервирует деньги повторно: возвращается исходный вывод со статусом `200` и заголовком
`Idempotent-Replayed: true`. Ключ действует в рамках пользователя. Без заголовка каждый запрос создаёт новый вывод.

```bash
curl -X POST localhost:4000/api/users/<id>/withdrawals -H 'content-type: application/json' \
  -H 'Idempotency-Key: 9f1c2d1e-...' \
  -d '{"tokenId":"<circle token id>","destinationAddress":"0xabc...","amount":"1.5"}'
```

Пример:

```bash
curl -X POST localhost:4000/api/users/<id>/withdrawals -H 'content-type: application/json' \
  -d '{"tokenId":"<circle token id>","destinationAddress":"0xabc...","amount":"1.5"}'
```

## Ключевые решения

**Один кошелёк Circle на пользователя.** Адрес кошелька служит адресом пополнения. Входящий перевод однозначно
относится к пользователю по `walletId`: не нужны memo/теги и не нужно переводить средства между кошельками. В Circle
у кошелька `refId = userId`, а `idempotencyKey = userId`, так что повтор запроса не создаст второй кошелёк.

**SCA-кошельки (по умолчанию).** На тестнетах газ для SCA спонсирует Circle Gas Station, поэтому для вывода
пользователю не нужен нативный ETH и сумма списывается ровно та, что указана. EOA можно включить через
`CIRCLE_ACCOUNT_TYPE=EOA`, но тогда на кошелёк нужно положить ETH для газа.

**Ledger — источник правды, баланс — его материализованная сумма.** Таблица `transactions` хранит все операции.
Баланс хранится в `balances` (строка на пару пользователь + токен: `available`, `incoming`, `outgoing`) и
обновляется триггерами на `transactions` в той же транзакции БД, что и сама операция. Поэтому:
- чтение баланса — поиск по первичному ключу, не зависит от длины истории. Замер на 300 тыс. операций
  одного пользователя: сумма по истории ~750 мс, чтение из `balances` ~0,8 мс; вывод (проверка + резерв) ~2,5 мс;
- баланс не может разойтись с историей: любая запись в `transactions` (SQL-функции, будущий код, ручная правка)
  проходит через триггер. Правило «какая операция как влияет на баланс» записано в одном месте —
  `tx_balance_effect()`;
- триггеры уровня statement с transition tables: дельты суммируются по паре (пользователь, токен), каждая строка
  баланса обновляется один раз за SQL-запрос. Построчный триггер переписывал бы одну и ту же строку N раз —
  массовая вставка 300 тыс. строк заняла бы минуты, а так ~4 с;
- строки балансов блокируются в фиксированном порядке — параллельные запросы не попадают во взаимную блокировку;
- `balance_drift()` пересчитывает балансы из истории и возвращает расхождения (ожидается пусто) — проверяется
  в тестах после всех сценариев, можно запускать как периодический аудит.

**История операций неизменяема — это гарантирует сама база, а не код.** Триггеры на `transactions`:
- факты операции (сумма, направление, пользователь, токен, адреса, время создания, ключ идемпотентности)
  не меняются никогда;
- операция только движется по жизненному циклу `pending → completed | failed`; id транзакции Circle
  записывается один раз; завершённая операция заморожена;
- удалить операцию нельзя — только вместе с её пользователем (каскад); `TRUNCATE` запрещён.

`balances` пишут только триггеры учёта: прямой `INSERT`/`UPDATE`/`DELETE` отклоняется. У публичных ключей
(`anon`, `authenticated`) нет никаких прав на таблицы с деньгами — даже на чтение и `TRUNCATE`, который RLS не
покрывает. Так даже бэкенд с ключом `service_role` или тот, кто этот ключ получил, не может переписать историю,
а баланс не может разойтись с ней. Не покрыто схемой: суперпользователь базы может отключить триггеры — от этого
защищают доступы к прод-базе и аудит.

**Денежные инварианты живут в БД.** Все изменения ledger проходят через SQL-функции:
- `create_withdrawal` блокирует строку баланса (`FOR UPDATE`), проверяет доступную сумму и вставляет
  pending-вывод в одной транзакции. Конкурентные выводы одного пользователя по одному токену сериализуются, двойное
  списание невозможно (есть тест на 5 параллельных запросов);
- `apply_circle_transaction` применяет снимок транзакции Circle идемпотентно и независимо от порядка. Финальные
  статусы не меняются, а pending двигается только вперёд по рангу состояния Circle. Вебхуки могут приходить
  повторно и не по порядку, это безопасно;
- `fail_withdrawal` помечает вывод, который Circle отклонил, и освобождает резерв.

**Защита от двойного списания — на трёх уровнях.**
- Разные выводы одновременно: `create_withdrawal` блокирует строку баланса (`FOR UPDATE`), проверяет сумму и
  резервирует в одной транзакции — второй поток ждёт и видит уже уменьшенный баланс.
- Повтор одного запроса клиентом: `Idempotency-Key` + уникальный индекс `(user_id, idempotency_key)`. Ключ
  проверяется под той же блокировкой; гонку параллельных повторов решает уникальный индекс. Форма вывода создаёт
  ключ на «намерение» (токен + адрес + сумма): повтор тех же данных идёт с тем же ключом, новые данные или
  следующий вывод — с новым.
- Повторная отправка в Circle: `idempotencyKey` = id записи вывода плюс поиск по `refId` перед повтором
  (см. ниже).

**Вывод в два шага: резерв, затем отправка.** Сначала средства резервируются строкой в ledger, затем идёт запрос в
Circle с `idempotencyKey = refId = id строки`. Если Circle недоступен, вывод остаётся `pending`, и reconciler
повторяет отправку с тем же ключом. Перед повтором он ищет перевод в Circle по `refId`, чтобы не отправить его
второй раз, даже если истёк срок idempotency key. После 5 неудачных попыток вывод помечается `failed`, а средства
возвращаются. Ответ 4xx от Circle сразу означает `failed`.

**Вебхуки.**
- Подпись проверяется по сырому телу: ECDSA SHA-256, `X-Circle-Signature`, публичный ключ из
  `/v2/notifications/publicKey/{keyId}`, ключи кэшируются.
- Дедупликация идёт по `notificationId` в таблице `webhook_events`, она же служит журналом.
- Бэкенд не доверяет полезной нагрузке: по `notification.id` он заново читает транзакцию из Circle API и применяет
  актуальный снимок.
- При ошибке обработки возвращается 5xx, и Circle повторяет доставку.

**Reconciler как страховка.** Вебхук может потеряться: туннель упал, подписку ещё не настроили. Поэтому раз в
`RECONCILE_INTERVAL_MS` фоновая задача:
1. переотправляет зависшие выводы;
2. обновляет pending-транзакции;
3. подтягивает новые транзакции всех кошельков с курсором по времени. Так находятся пропущенные пополнения.

Все пути идут через ту же идемпотентную функцию.

**Пополнение засчитывается только в `COMPLETE`.** До этого оно видно в истории как `pending` и в балансе как
`incoming`, но вывести его нельзя.

**Суммы — строки и `numeric`.** Ни на одном этапе нет float: API принимает и отдаёт строки, Circle — тоже
строки, Postgres хранит `numeric` без ограничения точности (точная арифметика, без округления и переполнения),
из PostgREST значения отдаются через `::text`. На фронте суммы сравниваются через `BigInt`.
- **Выводы:** не больше `decimals` значащих знаков после точки для токена (нули в конце не считаются) — больше
  знаков в сеть не отправить.
- **Входящие переводы:** Circle сообщает, что реально произошло в сети, поэтому сумма записывается точно как есть.
  Проверяется только формат. Если знаков больше, чем `decimals` в наших метаданных токена, это признак ошибки
  метаданных: пишется предупреждение в лог, но пополнение не теряется. Сумма в неверном формате не записывается:
  вебхук отвечает 5xx, а фоновая сверка пропускает только эту транзакцию и продолжает работу с остальными.
  Переводы с нулевой суммой (спам-токены) игнорируются.

**Мульти-токен «бесплатно».** Учёт ведётся по `token_id` Circle, метаданные токена (symbol, decimals) кэшируются
в таблице `tokens`. Если с фаусета придёт EURC, он появится отдельной строкой баланса.

**Свой тонкий клиент Circle вместо SDK.** Он работает на `fetch`, базовый адрес берётся строго из
`CIRCLE_BASE_URL`, idempotency keys выбирает приложение, а `entitySecretCiphertext` генерируется заново на каждый
запрос (RSA-OAEP SHA-256). Тот же клиент используется в mock-сервере и в тестах.

**Общий пакет `@circle-wallet/shared`.** В нём только типы, поэтому сборка не нужна. Контракт API один для бэкенда
и фронта.

**Без аутентификации**, как требует ТЗ: пользователь создаётся и выбирается из списка, выбор хранится в URL
(`?user=`). Ответы API не кэшируются браузером (без ETag), потому что UI их постоянно опрашивает.

**i18n на клиенте — `next-intl`**, языки `ru` (по умолчанию) и `en`, переключатель RU/EN в шапке. Язык хранится
в cookie `NEXT_LOCALE` (без префикса в URL, чтобы не ломать `?user=`); без cookie берётся из `Accept-Language`.
Ключи сообщений типизированы (`i18n/i18n.types.ts`): опечатка в ключе или пропущенный аргумент — ошибка
typecheck. Ошибки API переводятся по `error.code` (`insufficient_funds`, `network_error`, …), остальные
показываются как есть. Даты форматируются в языке интерфейса и часовом поясе пользователя. Бэкенд
не локализован: он отдаёт коды ошибок, а не тексты для пользователя.
